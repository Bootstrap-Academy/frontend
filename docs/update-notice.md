# In-app update notices

`UpdateNotice.vue` displays a short explanation with a direct link and a close button in the normal page flow. It never submits consent or calls an API. Public legal/intake routes suppress it so their purpose remains clear.

`UPDATE_NOTICE_WINDOW` in `composables/updateNotice.ts` defines a version and an inclusive start/exclusive expiry in UTC. The mounted component checks expiry every minute and releases its timer/listener on unmount. For a future notice, change the version, window, link and DE/EN translations together, and add the replaced version to `RETIRED_UPDATE_NOTICE_VERSIONS`. Previous version markers never suppress a new notice.

The notice is for people with an account: it appears once a signed-in profile is loaded. A visitor without a session sees none, so the landing page, the login and the registration start with what the visitor came for. Someone who opens the site signed out and then signs in sees the notice after the login. The login, the registration and the confirmation of the e-mail address never show it (`isSessionEntryRoute`): the form of the first two is still on screen when the answer starts the session, and an account whose address is not confirmed goes on from there to the confirmation, where the code comes first. The notice waits for the page that follows.

Only an explicit close stores `bootstrap-academy:update-notice:<version>:<subject>` in Local Storage. The subject is the validated, loaded account identifier. Earlier builds also showed the notice to visitors without a session and stored their close under the subject `browser`; nothing reads that marker any more, it never hides the notice of an account, and every app start removes it. Dismissal is per browser and account, with no server synchronization. Cross-tab storage events also hide the notice. If browser storage is unavailable, the App-owned set keeps the dismissal for the current App lifetime, including layout changes. Account switches invalidate stale close handlers.

`plugins/storage-cleanup.client.ts` removes dismissals that can no longer matter at every app start: markers of retired versions and the marker of a visitor for the current version always, the other markers of the current version once its window has ended. Unknown versions stay untouched, so an older open tab cannot erase the dismissal of a newer notice.

Run `node --test tests/update-notice.test.mjs` for who sees the notice (no session, signed in and open, signed in and closed), account isolation, reload, blocked storage, window boundaries, expiry, version changes and the real App/component/button contract in both languages. Check the actual page flow and anchor in a browser at mobile and desktop widths before publishing.

The link of the notice names a section of a long page. Two things carry a reader there. After a click, the router moves to the section; `middleware/route.global.ts` sends only targets without an anchor back to the top. On a direct call the page is rendered in the browser after the router has looked for the section, so `plugins/anchor.client.ts` goes there once the first page stands and stays with it while the footer and the fonts still arrive. `tests/anchor-navigation.test.mjs` covers both.
